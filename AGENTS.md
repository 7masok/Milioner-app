# Правила работы с «Складом» для ИИ и разработчиков

Перед изменениями прочитайте `docs/SITE-PASSPORT.md`. Это единый паспорт поведения,
дизайна, данных и проверок. На сайте та же версия доступна через
Настройки → Для разработчиков; отдельную копию текста в HTML не создавайте.

## Границы задачи

- Выполняйте текущую задачу владельца. Его явное новое решение имеет приоритет
  над зафиксированным старым поведением. Не запрашивайте повторное разрешение на
  уже согласованную работу.
- Сохраняйте поведение остальных разделов. Не делайте попутный редизайн,
  массовое переименование или переписывание общей логики ради локальной правки.
- Единый UI-стандарт — цель для новых и затрагиваемых элементов, а не разрешение
  выравнивать всё приложение за один раз. Применяйте утверждённый стандарт только
  в разделе текущей задачи; остальные экраны меняются отдельными согласованными задачами.
- При конфликте кода и паспорта выясните причину. Существующий баг не становится
  требованием; падение теста само по себе не повод ослаблять тест или правило.
- Изменение расчётов, модели данных, входа или внешних операций, выходящее за
  рамки запроса, сначала предложите владельцу с описанием последствий.
- Не удаляйте и не перезаписывайте рабочие данные для проверки гипотез. Тесты
  используют фикстуры и локальную среду. Не запускайте production-миграции,
  восстановление бэкапа, запись остатков/рекламы или изменение секретов без
  авторизации именно на соответствующую операцию.

## Обязательные свойства

- Первый вход по коду открывает Главную / Сегодня. Перезагрузка с действующей
  сессией сохраняет вкладку и поддерживаемые фильтры, не мигает экраном входа.
- В Товарах разрешён ровно один компактный настраиваемый фильтр-сортировка рядом с поиском: только «Количество продаж» или «Общая прибыль», один числовой период 1–365 дней и направление больше/меньше. Не возвращайте отдельные пресеты времени, старые dropdown-фильтры, сортировки по остатку/запасу/прибыли за штуку или отдельную стрелку. Выбранные показатель, дни и направление сохраняются и видны прямо на кнопке; сброс возвращает А→Я, но выбранный период остаётся видимым. Этот период — единый аналитический период всей вкладки: «Продано», запас в днях, «Прибыль», «Прибыль / шт.», карточка товара, «Ожидаемая прибыль с остатка» и «Прибыль в пути до покупателя» вместе с детализациями используют один `productRankSpec()`. Нельзя одновременно показывать фиксированные 30 дней/180 дней рядом с пользовательским периодом для тех же продаж и прибыли. Верхняя карточка «На FBO Ozon» по-прежнему отдельно переключает режим «только товары с положительным остатком FBO / все товары». Реклама конкретного товара учитывается только при однозначной привязке; нераспределённые расходы Kaspi/WB не разбрасываются по товарам. «В продаже» в карточке товара — только свободное к продаже количество после вычета резерва; при резерве отдельно показывается только «Резерв». Отдельный показатель «Физически» в компактном списке не показывайте. Основные остатки держатся в первой логической строке; «В пути», «На складе» и FBO Ozon — во второй. Старые WB-заказы за пределами 14-дневного окна нельзя оставлять с замороженным доставочным статусом: сервер отдельно перепроверяет их через WB status API и обновляет PostgreSQL.
- В Товарах поиск и новый ranking-фильтр не должны запускать повторный тяжёлый пересчёт складского состояния. Используйте готовый инвентарный снимок; статистику продаж/прибыли для выбранного числа дней догружайте отдельно и кэшируйте. Старые legacy-значения filter/sort/period из localStorage игнорируются; поддерживаются только новые `rankSort`, `rankDays`, `rankDirection`.
- Во вкладке «Цены» WB1/WB2 никогда не обращаются к Wildberries из браузерного открытия, переключения магазина, reload или ↻: UI читает только последний PostgreSQL-снимок Railway и серверную очередь изменений. Отдельный фоновый цикл для WB1/WB2 делает не более одного запроса категории «Цены и скидки» за слот примерно 15 минут (15 минут + запас), хранит `next_allowed_at`, ошибки, незавершённую пагинацию и снимок в PostgreSQL и уважает `X-RateLimit-Retry`/`Retry-After` даже после deploy/restart. Если нужна следующая страница `limit=1000`, она читается только в следующем слоте. Подтверждённые пользователем изменения цены/скидки не отправляются немедленно: они схлопываются по `nmID` до последнего состояния, показываются как ожидающие, затем одним пакетным POST уходят в ближайший разрешённый слот. `200` от upload не считать применением: следующий разрешённый слот проверяет `uploadID` через processed upload details, позиции без ошибки переходят в проверку снимком, а WB-ошибки сохраняются и не запускают слепой повтор того же значения. Общая цена при разных ценах размеров по-прежнему запрещена сервером. API-токены остаются только на сервере. Сортировка и скрытие позиций — клиентские и обратимые. Редактор отдельной позиции раскрывается inline внутри карточки; не возвращайте отдельный modal/bottom-sheet для редактирования цены. Одновременно раскрыта только одна карточка. Держите разворот компактным: без поясняющих абзацев и отдельной кнопки «Свернуть», поля в одну компактную строку где возможно, действия короткие «Сохранить» и «Скрыть». Для WB у товара может быть серверный флаг «Акции»: он разрешает только автоматизацию обычных `regular`-акций из публичного Promotions Calendar API. Сервер берёт `planPrice/planDiscount`, меняет скидку через существующую очередь и добавляет товар в акцию только после подтверждённой подходящей цены. Если подходящей `regular`-акции нет или остались только `auto`, сканер не имеет права сам откатывать скидку продавца; исходная скидка возвращается только при явном выключении флага «Акции». Ручная очередь всегда важнее промо-очереди; автоакции не угадывать и не эмулировать. Для WB-промо показывайте статус прямо на свернутой карточке: «В акции» только после подтверждения regular-акции, «Ждёт акцию» для включённой автоматизации без подтверждения и «Без акции» для выключенной. Массовый выбор WB должен поддерживать чекбоксы карточек, «Все» по текущему видимому списку и действия «В акцию»/«Убрать» без немедленного вызова WB. Для выбранных WB-позиций также доступно одно компактное действие «Ночь»: пользователь задаёт время начала/окончания и цену, а сервер хранит ежедневное расписание в PostgreSQL, ставит ночную цену и возвращает исходную цену только через существующую 15-минутную очередь. Возврат после сильного повышения делать подтверждёнными ступенями не более примерно ×1,9 вниз за шаг при текущем пороге карантина WB 2×, оставляя запас до границы. Ошибки `lower them gradually`/карантина не считать фатальными: пересчитывать следующий безопасный шаг. Проверять каждый `uploadID` перед дальнейшим изменением. Ручная правка цены имеет приоритет над ночным расписанием; ночное расписание имеет приоритет над промо-очередью. На свернутой карточке активное расписание видно компактно как время и цена. Promotions Calendar сериализуется по фазам `list → eligible → upload → verify`. Для текущего базового WB-токена лимит категории — один запрос в час на аккаунт продавца для всех методов календаря акций, поэтому каждый внешний шаг ставит следующий разрешённый запрос не раньше чем через час с небольшим запасом. Состояние фазы и курсор хранятся в PostgreSQL, а `X-RateLimit-Retry`/`Retry-After` всегда имеют приоритет и переживают deploy/restart. Не зацикливайтесь на первой акции: если товар не подходит, проверяйте следующие доступные `regular`-акции и выбирайте для товара подходящую с наименьшим снижением цены среди равноценных активных вариантов. Публичный WB API не позволяет получать товарную цену/добавлять товар для `auto`-акций; в таком случае интерфейс обязан явно показывать «Автоакции вручную», а не бесконечное «Ждёт акцию». После отдельного переключения «Акции» нажатие «Сохранить» без изменения цены/скидки не должно выдавать ошибку.
- Колокольчик, ИИ и обновление имеют место в исходной шапке; обновление не
  уничтожает свою иконку. Не возвращайте запоздалое перестроение шапки.
- Все обязательные runtime/compatibility-модули подключайте статически и до `initOwnerAuth()`. Не запускайте приложение, пока динамически подгружаемые скрипты ещё могут подменить `save`, `render`, складскую синхронизацию или marketplace hooks. Ozon FBO после загрузки владеет своей строкой статуса в шапке. Первый render Товаров обязан иметь один аварийный retry вместо вечного `Подготавливаю товары…`.
- Верхний блок «Сегодня» в Отчётах обязан учитывать Kaspi + WB1 + WB2 + Ozon. Для Ozon заказы распределяются по `created_at`, выкупы — только по реальному `delivered_date` у FBO-постинга; дневные итоговые выкупы и прибыль берутся из Ozon-финансовой сводки. Если точного `delivered_date` нет, не раскладывайте Ozon по выдуманному часу — показывайте дневной итог и признак неполной почасовой разбивки.
- В общем отчёте «Сегодня»/«Вчера» WB1/WB2 используют фактические live-выкупы, если финансовая детализация WB ещё отсутствует или отстаёт. Не подставляйте нулевые продажи. Показывайте известные сумму/количество, а неизвестные расходы и прибыль как «—»; для длинных периодов основным остаётся финансовый отчёт WB.
- Источник live-выкупов WB — серверный `/api/v1/supplier/sales`: синхронизируйте его примерно раз в 35 минут с persisted `last_change_date`/`next_allowed_at`, 5-минутным overlap и уважением 429 retry headers. Не привязывайте частоту внешнего вызова к 10-минутному циклу заказов и не вызывайте Statistics API из браузера.
- Не превращайте известную рекламу WB в `−реклама` как «прибыль», если продажи/финансовая детализация за период неизвестны. В таком состоянии показывайте рекламу отдельно, а приход/неизвестные расходы/прибыль оставляйте `—` или явно «данные продаж WB ожидаются».
- Compatibility-модули маркетплейсов не должны заменять современный `renderProducts`; они могут расширять данные/карточки через совместимые обёртки. Ошибка отрисовки вкладки не означает потерю связи с PostgreSQL: успешный складской fetch остаётся `онлайн`, а загрузка `/api/market-status` и `/api/orders` продолжается. При замене warehouse snapshot сохраняйте живой `serverMarketStatus`.
- PostgreSQL — источник подтверждённых бизнес-данных. Кэш склада до загрузки
  актуальной серверной ревизии доступен только для чтения. Сохраняйте проверки
  ревизий, учёт движений, резервов, FIFO и уникальности привязок.
- Финансы отделены от warehouse-state: сервер склада удаляет `personalFinanceAccounts`, `personalFinanceCategories`, `personalFinanceTransactions`, `personalFinanceLegacyImports`. Любая функция, заменяющая `state` складским снимком, обязана сохранить эти локальные финансовые ключи; складской watcher не может обнулять Финансы.
- При восстановлении вкладки «Финансы» не показывайте неподтверждённые `0 ₸` до hydration IndexedDB/сервера. После восстановления данных активная вкладка обязана перерисоваться. Локальный выбор режима/периода/даты аналитики сохраняется между reload.
- Предпросмотр импорта выписки не должен теряться, если во время классификации перевода нужен новый счёт. Создание такого счёта выполняется local-first, в валюте основного счёта выписки, после чего новый счёт сразу доступен в текущем переводе.
- Предпросмотр импорта выписки не должен теряться, если в списке категорий платежа нет нужной. Создание категории выполняется local-first поверх импорта и сразу выбирает её в текущей операции.
- Сохраняйте существующую проверку сессии и origin. Не помещайте код доступа,
  токены маркетплейсов, строки подключения или рабочие данные в документацию.
- Паспорт не загружается и не обрабатывается на рабочих страницах. Не добавляйте
  его в стартовые скрипты, предварительную загрузку, кэш service worker или
  фоновый опрос. Не подключайте ради него библиотеки, CDN или запросы к БД.

## Рабочий порядок

1. Проверьте текущую ветку, незакоммиченные изменения и актуальность базы.
2. Найдите реальную исполняемую функцию. Файлы совместимости могут переопределять
   функции `index.html`; проверьте порядок подключения и серверные преобразования.
3. Внесите минимальную правку. Если меняется согласованное поведение, обновите
   соответствующий раздел паспорта и только связанные проверки.
4. Запустите относящиеся к правке проверки и обязательный перед выпуском `npm test`.
   Не ослабляйте пройденные ранее гарантии ради зелёного результата.
5. Опишите в PR причину, результат, проверки и ограничения. Выпускайте обновление
   только в рамках авторизации владельца. Если оно выпущено через Railway,
   проверьте `SUCCESS` и совпадение коммита, прежде чем говорить «можно проверять».

Паспорт объясняет правила; автоматические тесты проверяют часть правил. Наличие
этих файлов не означает, что все возможные ошибки обнаруживаются автоматически.
