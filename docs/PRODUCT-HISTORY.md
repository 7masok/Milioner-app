# История товаров · 29.10.2026

В Товарах рядом с «Упаковкой» — «История изменений». В обычной карточке товара — «История товара». Общий журнал показывает и удалённые карточки; поиск по названию/ID, фильтры по объекту (карточка, партия, резерв, движение, продажа/возврат) и действию, по 50 событий с курсором. При переименовании поиск также учитывает текущее название, а события сохраняют имя на момент записи. Время — серверное, отображается по Алматы. Перед/после раскрываются внутри записи, ID позволяет различать одноимённые товары. Удаление одного ID не скрывает историю другого.

Миграция 151 создаёт независимые product_history и product_history_meta. AFTER-триггеры на warehouse_products/purchases/reservations/movements/sales фиксируют только подтверждённые изменения PostgreSQL, включая фоновые процессы, наборы, привязки, остатки, резервы и партии. Родительская связь по product_id не имеет внешнего ключа с каскадным удалением. При переносе партии на другой productId событие сохраняется у обоих товаров. Изменения внешних снимков остатков/цен маркетплейсов, не записанные в эти складские сущности, и локальные несохранённые попытки в журнал не входят.

Сначала сравниваются бизнес-документы без updatedAt/updated_at; одинаковое сохранение не создаёт событий и не хеширует повторно крупные фото. Реальные изменения записываются по полям с beforeExists/afterExists, чтобы отличать отсутствие от null. Крупные значения свыше 4096 символов хранятся отпечатком и размером; секретоподобные ключи исключены. Картинки/URL из истории не загружаются браузером, значения экранируются.

Существующий warehouse_audit в конце той же транзакции прикрепляет фактический источник процесса и ревизию к событиям txid_current(). Для операций без этой метки честно показана «Серверная запись», а канал из сущности показан отдельно. Общий код входа не позволяет определить конкретного человека: источник записи не выдаётся за авторство пользователя. Неудачная/отменённая транзакция не оставляет историю. Отдельных API для изменения/удаления журнала нет; он не является частью редактируемого warehouse-state.

На момент включения создаётся одно явно обозначенное исходное состояние каждого существующего товара. Это не поддельное событие его первоначального создания. Старые подробные события не восстанавливаются: прежний warehouse_audit содержал только хеш/ревизию, а не полевую историю. Повторное применение миграции не добавляет второй baseline. UI показывает точное время начала журнала из метаданных.

GET /api/product-history защищён действующей сессией владельца и доверенным origin, всегда no-store. Параметры q/productId/entity/action/before проверяются; SQL параметризован, LIKE-метасимволы экранируются, ID курсора передаётся строкой без потери точности. Ответ не меняет склад. Новый скрипт подключён статически до initOwnerAuth через серверное преобразование; index.html и расчёты соседних вкладок не переписываются.

Проверки: product-history.test.mjs запускает миграцию и настоящие PostgreSQL-триггеры в PGlite (dev-зависимость, продакшен остаётся на PostgreSQL); создание двух одноимённых ID, изменение, удаление, перенос партии, закупки/резервы/движения/продажи, no-op, rollback, источник/ревизия, повторная миграция, крупные фото, экранирование поиска, авторизация/origin, пагинация, XSS и запоздалые ответы UI. Обязателен полный npm test. Проверки используют только тестовые данные.

## Читаемый журнал

Поля и статусы показываются по-русски: «На складе → В продаже», «Дата поступления в продажу». Названия статусов совпадают с закупками. ID, ревизия и исходные JSON-значения вынесены в свёрнутые «Технические сведения» внутри изменений. Неизвестные поля обозначаются как дополнительные, исходные ключи и значения сохраняются в технических сведениях. Вложенные значения показаны списком с русскими подписями. Изменяется только отображение; серверная история не переписывается.

## Только события

Фоновые метки проверки/синхронизации и наблюдения остатков WB (`stockObservation`, `wbAmount`) исключаются рекурсивно перед сравнением. Только они изменились — нового события нет. Реальные изменения остатков склада, привязок, карточек, партий, резервов, движений и продаж остаются, в том числе созданные фоновым обработчиком. Читатель применяет ту же проекцию к старым записям до пагинации: старый шум скрыт без удаления аудита. Исходные состояния `baseline` не показываются как события. Миграция 152 не меняет складские данные и не удаляет историю.
